# AGENTS.md — точка входа для любого агента

**Проект:** «Лавка алхимика» (рабочее название, уникальность в каталоге проверить на S11) — казуальный 2D-симулятор алхимической лавки для **Яндекс Игр**.
**Движок:** Godot **4.7**, GDScript (статическая типизация), рендерер **Compatibility**, web-экспорт **однопоточный**.
**Визуальный стиль:** A — уютный сказочный мультяшный (`docs/art/ART_STYLE.md`).
**Язык общения с пользователем:** русский.

---

## 0. ГЛАВНОЕ ПРАВИЛО: сохраняй каждый шаг (требование пользователя, критично)

Ответ агента обрывается без предупреждения — так уже терялись целые сессии. Поэтому:
- **Начало работы:** первым делом прочитай `HANDOFF.md` в корне Pod (`/files/pod/HANDOFF.md`): что делается сейчас, чек-лист подэтапа, журнал по шагам. Затем продолжай с первого незакрытого пункта, ничего не переделывай.
- **После каждого шага**, который изменил хоть один файл (новый файл, правка, прогон humanizer, решение), сразу выполни:
  `python tools/pod_sync.py --quick --note "что сделано и что дальше"`
  Команда допишет строку в журнал `docs/HANDOFF.md`, закоммитит всё незакоммиченное (`wip: …`), обновит bundle и положит `HANDOFF.md`, `AGENTS.md`, `docs/PROGRESS.md` в Pod. Это секунды, экономить на этом нельзя.
- В начале подэтапа впиши его чек-лист в раздел «Сейчас» файла `docs/HANDOFF.md` и отмечай `[x]` по ходу.
- Не держи работу только в `/tmp` и в голове: результат шага, которого нет в Pod, для следующего агента не существует.
- Перед ответом пользователю — ещё один `--quick --note`, даже если подэтап не закончен.
- **Архив для GitHub — всегда свежий (требование пользователя, 31.10.2026: «сохранять как можно чаще, каждый чих»).** Сначала сохранение, потом следующая задача. В Pod всегда должен лежать архив, который пользователь распакует поверх своего репозитория и запушит: `outbox/alchemist_update_<метка GitHub>_to_v<версия>.zip`. Его пересобирает каждый `--quick`, если в Pod есть `outbox/GITHUB_BASE` (коммит и метка, на которых стоит GitHub пользователя). Этот файл пишет полный протокол с `--base`. Если `outbox/GITHUB_BASE` нет (новый Pod) или пользователь запушил новую версию (§2.2), в начале сессии запусти полный протокол `--base <тег sync с GitHub> --base-label <метка>`: он запишет базу. До этого никакой новой работы.

## 1. Как продолжить работу (строго по порядку)

0. Прочитай `HANDOFF.md` в корне Pod (§0).
1. Прочитай `docs/PROGRESS.md` — текущий подэтап и «Следующий шаг». В Pod это `project/docs/PROGRESS.md`; `docs/` в корне Pod — такое же зеркало. Что и когда выгружено последним — `archive/LAST_SYNC.txt`.
2. Прочитай последние 3 записи `docs/DEVLOG.md`.
3. Найди подэтап по ID в `docs/PLAN.md` (формат `S<этап>.<подэтап>`), прочитай «Сквозные правила».
4. **Сверься с GitHub и проверь `inbox/` в Pod** (§2.2): пользователь мог запушить правки (код, `*.uid`, `*.import`), а в `inbox/art/` — положить финальную графику. Обработай это первым.
5. Восстанови рабочую копию:
   - если `/tmp/work/repo` уже есть (песочница не перезапускалась) — **не клонируй поверх**: `git status` и `git log` покажут незакоммиченную или невыгруженную работу прошлой сессии; сравни HEAD с `archive/LAST_SYNC.txt`, доведи и выгрузи;
   - иначе: `git clone /files/pod/archive/alchemist_repo.bundle /tmp/work/repo` (история агента со всеми тегами), затем `python tools/placeholder_pngs.py` — в рабочей копии агента нет настоящих PNG (§2.3);
   - если bundle в Pod нет (новый Pod) — восстанови текстовые файлы с GitHub по §2.3.
6. Работай в `/tmp/work/repo`. После каждого подэтапа — «Протокол сохранения» (§2.1).

> С v0.0.1 документы (`AGENTS.md`, `docs/`, `tools/`) живут **в репозитории**. Pod хранит зеркало всего дерева в `project/`, а `AGENTS.md`, `docs/`, `tools/` в корне Pod — зеркала для быстрого доступа. Правь только репозиторий, зеркала обновляет `tools/pod_sync.py`.

## 2. Протокол сохранения и обмена с GitHub

У Computer нет интернета, у пользователя — есть. **Источник истины — репозиторий пользователя на GitHub**, обмен идёт через Pod.

### 2.1 Агент → пользователь (после КАЖДОГО подэтапа и не реже чем каждые ~10 изменённых файлов)
**Страховка:** после каждого шага — `python tools/pod_sync.py --quick --note "…"` (§0). Сессия может оборваться в любой момент: работа, которой нет в Pod, потеряна для следующего агента.

1. Обновить `docs/PROGRESS.md`, дописать `docs/DEVLOG.md`, отметить `docs/PLAN.md` — **до коммита**, чтобы они попали в архив.
2. `python tools/validate_project.py` — без ошибок.
3. Коммит в `/tmp/work/repo` (сообщение: `S<ID>: <что сделано>`), тег версии `v0.X.Y` (версия — в `project.godot`, `config/version`).
4. `python tools/pod_sync.py --id S<ID> --slug <snake_case>` — делает всё ниже автоматически:
   - `archive/alchemist_latest.zip` — чистое дерево **без `.git`** (для пользователя);
   - `archive/history/alchemist_v<версия>_<ID>_<slug>.zip` — снапшот (хранить последние 10);
   - `archive/alchemist_repo.bundle` — `git bundle create ... --all` (история для агентов);
   - `outbox/patches/v<версия>/` — `git format-patch` с прошлой выдачи (метка `outbox/patches/LAST_PATCHED`);
   - `project/` — зеркало дерева; `AGENTS.md`, `docs/`, `tools/` в корне Pod;
   - `archive/LAST_SYNC.txt` — версия, подэтап, коммит, время.
   - `outbox/alchemist_update_v<версия>.zip` — изменённые файлы с прошлой выдачи (основной способ для пользователя).
   - если GitHub отстаёт на несколько выдач — добавить `--base <тег на GitHub> --base-label <тег>`: сводный `outbox/alchemist_update_<тег>_to_v<версия>.zip` ставит всё одним архивом.
5. Пользователь распаковывает `alchemist_update_v<версия>.zip` поверх проекта или применяет патчи (`git am`) и пушит — `README.md`, «Дальнейший обмен». Bundle — только страховка истории агента: с историей GitHub он не совпадает.

### 2.2 Пользователь → агент
Репозиторий: **https://github.com/katabasis1/alchemist**, ветка `main`. Пользователь пушит туда (в т. ч. файлы, созданные Godot: `*.uid`, `*.import`, пересохранённые `.tscn`); бинарники, которые агенту нужны (финальная графика), кладёт в `inbox/art/` Pod.
Агент в начале сессии: список файлов и SHA — `https://api.github.com/repos/katabasis1/alchemist/git/trees/main?recursive=1` (веб-инструмент), сравнить SHA текстовых файлов с `git ls-files -s` рабочей копии; отличающиеся скачать с `raw.githubusercontent.com` (≤16 URL за вызов), проверить `git hash-object`, закоммитить в ветке `sync/<дата>` («sync: GitHub <sha>»), слить (приоритет — версии пользователя для `*.uid`, `*.import`, пересохранённых `.tscn`). Картинки из `inbox/art/` → `assets/` под теми же именами, обработанное → `inbox/_done/<дата>/`. Всё — в DEVLOG.

### 2.3 Что агент не может забрать с GitHub
Веб-инструмент отдаёт текст; бинарные файлы (и base64 из API `git/blobs`) обрезаются примерно на 40 КБ. Поэтому **PNG/JPG в git-истории агента нет**: они перечислены в `.git/info/exclude`, а для валидатора `tools/placeholder_pngs.py` создаёт прозрачные заглушки нужного холста (тоже в exclude). Следствия: ZIP/зеркала агента — без картинок; патчи и `alchemist_update_*.zip` картинок не трогают, пока агент сам не добавил новую графику (тогда настоящий PNG коммитится как обычно и в exclude не попадает).
Сырые файлы с GitHub через веб-инструмент приходят байт-в-байт (проверено `git hash-object`).

> `/tmp` очищается при перезапуске песочницы — всё несинхронизированное в `/files/pod` теряется.
> `/files/pod` — медленное хранилище (GCS): работать в `/tmp/work`, синхронизировать пачкой.

## 3. Правила архитектуры и контента (не нарушать)

1. **Композиция, а не наследование.** Сущность = сцена из узлов-компонентов. Скрипты наследуют только базовые классы движка (`Node`, `Node2D`, `Control`, `Resource`…). Своих иерархий классов нет.
2. **Никаких объектов, созданных кодом.** Все объекты — `.tscn`-сцены и узлы. Разрешено: `PackedScene.instantiate()` готовых сцен, `create_tween()`, `get_tree().create_timer()`. Запрещено: собирать деревья узлов через `X.new()` + `add_child()`.
3. **Данные — в ресурсах** (`.tres`). Никаких «магических чисел» в коде.
4. **Связи:** сигналы вверх, вызовы вниз; ссылки на узлы — через `@export`; `EventBus` — только для глобальных событий.
5. **Один компонент — одна ответственность.** В шапке скрипта: назначение, сигналы, зависимости.
6. **Тексты:** только через ключи локализации (`localization/strings.csv`, ru/en). **Каждый текст, который видит игрок, проходит humanizer** до попадания в CSV: ru — `tools/humanizer/ru/SKILL.md` + `python tools/humanizer/ru/scripts/check_facts.py до.txt после.txt`; en — `tools/humanizer/en/SKILL.md`. Ключ добавляется в `localization/humanized.txt`. Касается и промо-текстов (описание игры, «Как играть»).
7. **Графика: временная + промпт сразу.** Новый графический элемент → временная генерация (на фоне `#FF00FF`, для розового/фиолетового — `#00FF00`) → `tools/art/cutout.py` → PNG по контракту из `docs/art/ASSET_REGISTRY.md` → **в тот же подэтап** промпт для ChatGPT Image в `docs/art/PROMPTS.md` (стилевой префикс из `ART_STYLE.md`). Финальная картинка заменяет временную **под тем же именем и размером** — сцены не правятся.
8. **ИИ рисует «пустые» статичные объекты.** Жидкости, цвета свойств, пар, пузыри, свечение — шейдеры и частицы.
9. **Juice:** у каждого значимого действия минимум 2 канала отклика.
10. **Числа** — по Numbers Policy: «стартовое значение + план проверки» (`docs/GDD.md`, `EconomyConfig`).
11. **Шейдеры:** свои или с godotshaders.com только под **CC0/MIT** (GPL не брать). shadertoy.com — по умолчанию CC BY-NC-SA 3.0 (некоммерческая) → только как идея и собственная реализация, либо код с явно разрешающей лицензией автора. Каждое заимствование — в `docs/THIRD_PARTY.md`.
12. **Яндекс-требования** — `docs/YANDEX_CHECKLIST.md` (без чёрной магии, жестокости к животным, религиозных символов).
13. **Визуальный шейдер — сначала референсы (требование пользователя).** Прежде чем писать визуальный шейдер (новый или заметную переделку), сгенерировать картинки «как это будет выглядеть в игре» — в стиле игры (`docs/art/ART_STYLE.md`), с настоящими ассетами сцены как референсами для генерации. Сохранить их в `docs/art/refs/ref_<тема>_*.jpg`, записать в HANDOFF/DEVLOG, что из них берём (форма, цвета, свет, движение), и только потом писать шейдер, сверяя результат с ними (numpy-макет `tools/art/*_preview.py` рядом с референсом). Без референсов шейдер не начинать.

## 4. Ограничения окружения

- **Computer без интернета** — решение пользователя: доступ не запрашивать. Godot недоступен → проверка валидатором + пользователь открывает проект на контрольных точках (M0–M5) и запускает проверочные сцены `scenes/debug/*` (F6), присылая вывод Output.
- **Веб-инструмент агента (вне Computer) интернет видит**: им читаются GitHub (§2.2) и документация. Его ответы сохраняются в `/files/conversation/.tool_outputs/` — оттуда их берёт Computer.
- Не создавать вручную `.godot/` и `*.import`. В `.tscn/.tres` не выдумывать `uid://` — ссылки по `path`.
- Временная графика — инструмент генерации изображений → `tools/art/cutout.py` (OpenCV/Pillow).
- Звуки MVP — синтез в Computer (numpy → ffmpeg, ogg/vorbis).
